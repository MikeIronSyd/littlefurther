### R11 experiment and actual result

The experiment ran in the ignored `.local/research/runtime-check/` directory as synthetic research, not production scaffolding. Safe source-only reproduction inputs/report/results are preserved under [experiments/runtime-feasibility](experiments/runtime-feasibility/REPORT.md). Exclude credentials, temporary databases, dependencies, builds and secrets from tracked source. The following required protocol was satisfied:

1. Select exact maintained versions for Node-compatible Express 5, TypeScript/Vite, Better Auth and better-sqlite3 13.0.3. Confirm package engines and declared integration support; resolve a lockfile without silently ignoring engine/conflict errors.
2. Load the native SQLite driver on this Windows/Node runtime; create/read/write a temporary DB and prove commit/rollback behavior. Record whether prebuilt loading succeeds or an unplanned toolchain is needed.
3. Configure an ESM Express 5 local server with the documented auth handler ordering, exact local origin and maintained protections. Initialize the Better Auth schema in temporary SQLite by the documented supported mechanism.
4. With synthetic credentials, sign up/sign in two accounts, read distinct sessions, reject unauthenticated protected access, sign out and prove the old session is unusable. No email is sent and neither identity is presented as verified.
5. Resolve any integration failure or revisit the stack. Record the reproducible combination and remaining nonblocking implementation work. Only mark R11 satisfied when its required observed results exist; a successful package install alone is insufficient.

Actual final commands, all exit 0: `pnpm install --frozen-lockfile --ignore-scripts --reporter=append-only`; `pnpm exec tsc -p tsconfig.json`; `node compiled/fixture.js`; `pnpm exec vite build`. Full arguments/timestamps/hashes are in [verification.json](experiments/runtime-feasibility/verification.json); all 35 assertions and cleanup state are in [latest-result.json](experiments/runtime-feasibility/latest-result.json).

Environment: Windows 10.0.26300 x64, PowerShell 7.6.5, Node 24.19.0, pnpm 11.19.0. Pins: Express 5.2.1, Better Auth 1.7.7, better-sqlite3 13.0.3/native SQLite 3.53.4, TypeScript 7.0.2, Vite 8.3.3, @types/node 24.19.1, @types/express 5.0.6, @types/better-sqlite3 9.6.0, bun-types 1.4.2. Manifest SHA-256: `8bd3cbef0cf99a8006ecc17be92027652d55164c59048fb0a6e64af0ec78389a`; lockfile SHA-256: `73f5b51a8320993033be604a3ba14d94ba8bb9040052bbcb587cb44e4be82833`.

Observed: native SQLite load/WAL, transaction commit/rollback, repeatable auth migrations, Express named-wildcard handler ordering, two synthetic signups/signins and distinct sessions, `emailVerified: false`, anonymous rejection, wrong/short-password rejection, unsafe-origin/callback rejection, sign-out revocation without revoking the other user, and retained rows/sessions after server/database close/reopen in the same Node process. Final server and database were closed. The minimal browser ES module compiled/bundled without a UI framework; it was not a product screen or frontend implementation.

Retained failures: strict TypeScript initially could not resolve `bun:sqlite`; loading full @types/bun globals then caused unrelated Node/Bun declaration conflicts. The official pinned `bun-types` package with `types: ["node", "bun-types/sqlite"]` resolved this with strict settings, no `skipLibCheck` and no handwritten shims. An unsupported pnpm-remove flag also failed during cleanup; its individual exit was not captured. Manifest cleanup and the final frozen install independently passed. See the report rather than replacing this history with a blanket first-try-success claim.

Limits: the frozen install reused this host's environment, not a clean machine. Persistence exercised same-process server/connection reopening, not process/machine reboot. The fixture used an ephemeral in-memory secret; persistent product secret configuration remains an implementation requirement. No real product workflow, peer authorization, browser cookie behavior, localization/accessibility, disconnected-internet operation, adoption or performance target was tested. Exact application migration, sharing, authorization and concurrency checks remain acceptance tests.

### Assumptions, hypotheses and evaluation boundaries

- **User decisions:** broad learners, local server demo, feature/language scope, curated content, no runtime AI and image-first process are settled requirements, not research guesses.
- **Working assumptions:** the learner can enter or select appropriate material, estimates can be edited, and a local demo can use synthetic accounts. These constrain the PoC; they do not establish material quality for unknown courses.
- **Hypotheses:** smaller actions, retained visible work, manageable restart and optional support may make continuing easier. No measured engagement or retention effect exists.
- **Unmeasured alternatives:** no study of calendar/LMS/chat workarounds has established comparative superiority.
- **Future optional research:** if volunteers are available, observe three 15–20 minute sessions on creating a plan, restarting, explaining progress and identifying shared/private content. Record unassisted/assisted/failed outcomes and confusion; do not recruit or message anyone automatically. User research is valuable evaluation but was not selected as a pre-implementation prerequisite.
